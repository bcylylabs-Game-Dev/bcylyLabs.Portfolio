Find your way through the package: setup, network configuration, runtime integration and verification.

Package manual · Version 1.0.0 · Reviewed 30 October 2026.

Configure advertising from one Hub, integrate a provider-neutral runtime API and test the player experience with an interactive simulator. This manual covers the package itself and can be used with any Unity game.

Scope and compatibility#

The source was reviewed in Unity 6000.3.6f1. The package README declares Unity 2021.3 LTS or higher, but that broad compatibility range has not been verified here. Native SDK versions have their own requirements and must be compiled/tested explicitly.

Screenshots show the supplied editor tools and sample configuration. The pictured 2-second pacing values, missing-SDK badges, placeholder IDs and test IDs are examples, not a recommended live configuration.

This documentation describes existing behavior. Important consent, session attribution and native lifecycle gaps are explained where relevant and collected in the testing chapter. They are not fixed by creating this manual.

Setup & workflowChapter 02

User Guide

Configure the Hub, select a provider, connect ad formats and test the player experience.

1. Open the Monetization Hub#

Open Tools > Bcyly Labs > Bcyly Monetization > Monetization Hub. The Hub creates or loads a MonetizationSettings asset, ensures provider containers exist and presents these tabs:

TabPurpose
General & PacingEnabled formats, startup loads, cooldowns and rewarded watchdog settings
Dummy (Mock)Simulator banner, timing and delayed reward controls
AdMobSDK setup, app IDs, unit IDs and app-open configuration
AppLovin MAXSDK setup, banner options and per-platform unit IDs
LevelPlaySDK installation, app keys and per-platform unit IDs
Unity AdsSDK installation, game IDs, placement IDs and test mode
DiagnosticsConfiguration checks and setup hints

Opening a network tab does not activate it. The Active Monetization Provider dropdown selects the runtime provider. An SDK Missing badge means the editor did not detect the expected dependency; filling IDs does not install an SDK.

Settings asset selection

The default asset path is Assets/bcylyLabs/Monetization/MonetizationSettings.asset. The Hub and several build utilities choose the first asset returned by an editor type search. If you keep multiple settings assets, verify which one the Hub edits and which one your bootstrap references.

Runtime initialization requires an explicit settings asset. There is no automatic Core bootstrap that discovers the Hub asset. Assign it to your own startup component; a complete example appears in the developer chapter.

2. Configure formats and pacing#

Use General & Pacing to choose the ad experience before selecting a live provider.

SettingEffect
Debug ModeStored configuration flag; most logging and SDK test behavior are not controlled by it in this version
Load Ads On StartAfter successful initialization, requests enabled rewarded/interstitial ads and shows an enabled banner when allowed
Banner EnabledAllows banner show through the manager
Interstitial EnabledAllows interstitial requests through the show workflow
Rewarded Video EnabledAllows rewarded requests/shows
App Open EnabledGates manager app-open API; AdMob's internal foreground path currently bypasses this gate
First Launch DelayInitial interstitial cooldown after each initialization, not a persisted once-per-install delay
Interstitial IntervalShared minimum interstitial pacing interval
Rewarded Shield DelayInterstitial cooldown applied when a rewarded session resolves, including a false result
Show-to-Display TimeoutResolves an unpresented rewarded session as false after the configured interval

The source defaults for first delay, interval and rewarded shield are 45, 30 and 45 seconds respectively. Those defaults are not universal UX recommendations. The screenshot uses short demonstration values so behavior is easy to test.

Implementation note

Do not interpret the Hub's “frequency capping” label as persisted per-user or per-placement impression caps. Core pacing uses one runtime timestamp; any level/session caps must be implemented in your game or mediation configuration.

With Load Ads On Start disabled, call RequestRewardedVideo when you need to preload rewarded. There is no public facade RequestInterstitial method: calling ShowInterstitial while not ready returns false and requests one for a later attempt.

3. Use the Dummy simulator#

Choose Dummy in the active-provider dropdown and open Dummy (Mock). No native ad SDK or network credentials are required.

ControlPurpose
Banner Position / HeightControls the mock banner and reported layout height
Interstitial CountdownDelay before the mock interstitial can be closed
Rewarded DurationMock rewarded progress timing
Simulate Late RewardExposes a delayed-reward outcome in the mock UI

Enter Play Mode with an initialized manager, then call the runtime APIs from your controls or use the supplied demo scene. Show an interstitial, complete a rewarded ad and close one early. When late simulation is enabled, select the late-reward outcome and inspect both the initial callback and late-reward event.

Dummy creates an interactive Canvas simulator. It does not prove real SDK installation, fill rates, native threading, privacy forms or build compatibility. Its consent provider is currently registered after the initial consent gather, so Dummy privacy behavior is not evidence that native consent startup is correct.

4. Configure Google AdMob#

Open the AdMob tab. The Hub offers a Google Mobile Ads Unity package download/import, official sample IDs and an action to synchronize app IDs into Google Mobile Ads settings.

  1. 01
    Import a supported Google Mobile Ads SDK and its required native dependencies.
  2. 02
    Use sample ad units or properly configured test devices while developing.
  3. 03
    Set Android and iOS App IDs separately; these identify the application and use the ~ separator.
  4. 04
    Set per-platform banner, interstitial and rewarded Ad Unit IDs, which use the / separator.
  5. 05
    Synchronize app IDs to the SDK's settings asset and inspect the generated native configuration.
  6. 06
    Configure consent before native initialization and test it on devices.
  7. 07
    Select AdMob as active only when the adapter compiles and its requirements are satisfied.

App-open controls

The AdMob container has its own Use App Open Ad setting in addition to the global format flag. App-open units and expiration duration are available when configured.

Implementation note

The current internal foreground handler can bypass the global flag and your own resume policy. It also lacks complete close/failure/reload handling. Correct those lifecycle paths and choose one owner for resume policy before using app-open in a live build.

Under-age tag and test configuration

The under-age field is forwarded by AdMobUMPProvider when that provider is actually created and registered. It does not wire consent automatically or replace your audience configuration. Debug Mode does not put AdMob into test traffic mode; sample IDs/test-device configuration do that.

The included installer points to a specific SDK release rather than guaranteeing compatibility with every newer release. Validate the chosen SDK version instead of treating the installed badge as an API compatibility check.

5. Configure AppLovin MAX#

Use the MAX tab to import the SDK and enter real ad unit IDs separately for Android and iOS. Values such as banner, interstitial and rewarded in the screenshot are placeholders.

Complete SDK account/application setup, initialization requirements and any mediated network setup using MAX's own integration tools. This package's container only supplies its exposed unit IDs/options; it is not a full mediation dashboard or SDK-key manager.

Implementation note

The current handler always creates its banner at BottomCenter, and Use Adaptive Banner is stored but unused. Do not assume choosing a different position or enabling that option changes native rendering until the handler is updated and tested.

Interstitial callbacks currently report dispatch rather than close. Follow the lifecycle notes in the developer chapter before using completion callbacks to resume a game flow.

6. Configure Unity LevelPlay#

The LevelPlay tab offers installation through Package Manager. Configure Android/iOS app keys and the banner, interstitial and rewarded unit IDs corresponding to the correct application.

The adapter targets the modern Unity.Services.LevelPlay API. Detecting an old IronSource folder does not establish compatibility with this API.

Implementation note

The current source also has a LevelPlay namespace collision: static SDK calls must use an explicit alias or fully qualified SDK class. Fix that conditional compile blocker before activating the provider, then compile against a deliberate SDK version and validate native callbacks.

App-open is not implemented by this adapter. Empty keys/unit fields in the screenshot are configuration examples, not a functioning network setup.

7. Configure Unity Ads#

The Unity Ads tab installs com.unity.ads through Package Manager. Enter the Android and iOS game IDs and the placements corresponding to your dashboard.

Test Mode is passed to the Unity Ads initialization API. Banner/interstitial/rewarded placement fields are shared across the container; they are not separate Android/iOS pairs. Select the values appropriate to your target or maintain a deliberate per-platform configuration workflow.

Unity Ads implements banners, interstitials and rewarded video here. App-open queries return false and show calls do nothing. Avoid configuring identical interstitial/rewarded placement IDs: callback routing distinguishes these by the configured IDs.

8. Add a bootstrap and game controls#

Create a component that references MonetizationSettings and calls await MonetizationManager.InitializeAsync(settings) once. Keep a single startup owner and observe the result before requesting ads.

Use ShowBanner, HideBanner and DestroyBanner for banner controls. Use CanShowInterstitial before a natural transition, and IsRewardedVideoLoaded before showing an optional reward offer. A false result must leave the player able to continue without assuming an ad was watched.

Implementation note

Do not add gameplay rewards to both the completion callback and a second general ad-closed listener. A closed ad is not proof that a reward was earned. See the runnable scripting examples in Developer Reference.

9. Configure no-ads and safe area#

SetNoAds(true) enables permanent no-ads. SetTimedNoAds(seconds) enables a temporary period. Both preserve voluntary rewarded availability while suppressing banners, interstitials and app-open through the manager.

SetNoAds(false) and DisableNoAds() clear both permanent and timed access. A timed grant extends to the later of the existing expiry and now plus duration; it does not add the duration to the old expiry.

When no-ads becomes active, the package destroys the visible banner and resets its layout state. Expiration currently changes the getter result without emitting an automatic expiry event or restoring the banner. Your integration must account for this limitation.

SafeAreaAdapter exposes banner height, position, a change event and an adjusted screen Rect. It does not automatically attach a layout component to your Canvas. Native height units and some position options currently need correction; test real high-DPI devices before relying on banner avoidance.

10. Privacy controls and diagnostics#

Add PrivacyOptionsButton to a Unity UI Button or call ShowPrivacyOptions from your own settings UI. The component disables itself while the form request runs and re-enables on callback. It does not perform consent registration or automatically reflect whether the network requires an entry point.

Native UMP/ATT classes exist but are not registered by normal package startup, and the manager ignores the gather result. Wire and enforce the intended eligibility flow before live SDK requests. An editor fallback success is only a simulation.

Use Diagnostics for SDK/configuration hints. Green checks do not establish correct consent, current platform submission requirements, successful native output or working rewards. Follow Testing and Troubleshooting before release.

11. Manage SDKs carefully#

The Hub can install/import and remove supported dependencies. Back up your project and check dependency ownership before removing an SDK: the current uninstaller can delete resolver folders shared by other plugins.

UPM removal paths for Unity Ads and LevelPlay can leave the active provider pointing at the removed SDK. After a removal, explicitly recheck the active setting, symbols, assembly references and Console. Do not rely on “zero compile errors” messaging as verification.

Runtime referenceChapter 03

Developer Reference & API Examples

Integrate ads through the public API, events, rewarded callbacks and no-ads controls.

Runtime namespace: bcylyLabs.Monetization. The examples below use the shipped public facade. Example components are separate scripts; adjust their filenames to match their class names.

1. Architecture and startup#

text
Game bootstrap / UI
    -> MonetizationManager
       -> MonetizationSettings + selected ProviderContainer
       -> IAdProviderHandler
          -> Dummy / AdMob / MAX / LevelPlay / Unity Ads
       -> RewardedSessionTracker + watchdog
       -> NoAdsManager / ConsentManager / SafeAreaAdapter
       -> MainThreadDispatcher

InitializeAsync sets up common utilities, constructs the selected handler, gathers registered consent, initializes the provider and optionally loads initial ads. The current implementation does not enforce the consent result; that integration needs correction before live requests.

There is no shared in-flight initialization task, shutdown API or complete static reset. Use one startup owner; avoid concurrent initialization or runtime network switching. If the selected adapter is unavailable, initialization returns false rather than automatically selecting another network. Native initialization exceptions can propagate to the caller.

Bootstrap example

This component initializes the package once from an Inspector reference. It does not implement the missing native consent integration.

csharp
using System;
using UnityEngine;
using bcylyLabs.Monetization;

public sealed class MonetizationBootstrap : MonoBehaviour
{
    [SerializeField] private MonetizationSettings settings;

    private async void Start()
    {
        if (settings == null)
        {
            Debug.LogError("Assign MonetizationSettings in the Inspector.");
            return;
        }

        if (MonetizationManager.IsInitialized) return;

        try
        {
            bool ready = await MonetizationManager.InitializeAsync(settings);
            Debug.Log(ready
                ? "Ads ready: " + MonetizationManager.ActiveProviderName
                : "Ad initialization failed.");
        }
        catch (Exception error)
        {
            Debug.LogException(error);
        }
    }
}

Attach one instance to your startup scene and assign settings. The IsInitialized check avoids a completed duplicate initialization, but does not guard two callers starting at the same time. Centralize that ownership in your application.

There is no public RequestInterstitial facade method, cancellation token overload, global fullscreen-busy property or built-in reward wallet. Provider interfaces expose lower-level requests, but bypassing the facade also bypasses its policies.

3. Interstitial integration#

Place interstitials at deliberate transitions in your own game. A readiness query is a snapshot and is not a reservation.

csharp
using UnityEngine;
using bcylyLabs.Monetization;

public sealed class InterstitialExample : MonoBehaviour
{
    public void TryShowAtTransition()
    {
        if (!MonetizationManager.IsInitialized) return;

        MonetizationManager.ShowInterstitial(accepted =>
        {
            Debug.Log("Interstitial result: " + accepted);
        }, "level_transition");
    }
}

The callback meaning is currently provider-dependent: AdMob/MAX/LevelPlay invoke success after dispatch, while Unity Ads/Dummy generally invoke it after completion. Do not treat true as a universal “ad has closed” barrier. AdMob's current immediate callback also triggers premature reload/destruction through the manager; fix lifecycle semantics before shipping this flow.

If not loaded, ShowInterstitial returns false and requests one for a future opportunity. ignorePacing: true skips the timestamp check but still respects initialization, format enable and no-ads. The placement string is not forwarded to provider APIs or used for per-placement caps in this implementation.

4. Rewarded integration#

Offer an explicit player choice and grant a reward only when the earned callback is true. Use a gameplay method that knows the offered reward; the package does not persist application rewards.

csharp
using UnityEngine;
using UnityEngine.Events;
using bcylyLabs.Monetization;

public sealed class RewardedOfferExample : MonoBehaviour
{
    [SerializeField] private UnityEvent onRewardEarned;
    private bool requestPending;

    public void ShowOffer()
    {
        if (requestPending) return;

        if (!MonetizationManager.IsRewardedVideoLoaded())
        {
            MonetizationManager.RequestRewardedVideo();
            Debug.Log("Rewarded ad is not ready. Try later.");
            return;
        }

        requestPending = true;
        MonetizationManager.ShowRewardedVideo(earned =>
        {
            requestPending = false;
            if (earned) onRewardEarned?.Invoke();
            else Debug.Log("Reward was not confirmed by this callback.");
        }, "optional_reward_offer");
    }
}

The local requestPending flag prevents repeated taps on this component. It does not fix the shared tracker's session bugs, provide durable transaction deduplication or recover callbacks across app exit. Handle view destruction and changing reward context in your application.

Reward lifecycle

text
Idle -> Requested -> Showing -> Closed -> Completed
             |                    |
             -> Failed            -> wait briefly for reward

Reward before close is remembered; close resolves success. Close before reward starts a configurable grace timer. After that timer expires, the normal callback is false. A later native reward can emit a separate LateRewardData event.

Current limitations: Closed is not treated as busy, native events carry no session token, mismatched provider events are accepted, and duplicate late rewards can emit repeatedly. Correct these before relying on once-only reward guarantees. The show-to-display watchdog stops after display; a missing close event can leave a session unresolved.

5. Events and late rewards#

EventSignatureUse
OnAdLoadedAction of AdTypeRefresh readiness indicators
OnAdDisplayedAction of AdTypeObserve a reported presentation
OnAdClosedAction of AdTypeObserve format close notifications
OnAdSuppressedAction of AdType and stringReport no-ads suppression; not every blocked request emits it
OnNoAdsStateChangedAction of boolRefresh entitlement-dependent UI
OnLateRewardReceivedAction of LateRewardDataReconcile a delayed native reward after initial false outcome

AdType values are Banner, Interstitial, RewardedVideo and AppOpen. App-open event coverage is incomplete, and some provider events are posted to the main thread while others are invoked directly. Keep observers exception-safe and centralize Unity-thread delivery when extending adapters.

csharp
using UnityEngine;
using bcylyLabs.Monetization;

public sealed class AdEventExample : MonoBehaviour
{
    private void OnEnable()
    {
        MonetizationManager.OnAdLoaded += HandleLoaded;
        MonetizationManager.OnLateRewardReceived += HandleLateReward;
    }

    private void OnDisable()
    {
        MonetizationManager.OnAdLoaded -= HandleLoaded;
        MonetizationManager.OnLateRewardReceived -= HandleLateReward;
    }

    private void HandleLoaded(AdType type)
    {
        Debug.Log("Loaded: " + type);
    }

    private void HandleLateReward(LateRewardData data)
    {
        Debug.Log("Reconciliation needed: " + data.SessionToken.Id);
        // Resolve a retained offer context and compensate exactly once.
        // This logging example deliberately does not grant a second reward.
    }
}

LateRewardData contains SessionToken, Placement, ProviderName, DelaySeconds and TimestampUtc. AdSessionToken contains Id, Placement and CreationTimestamp. Normal public earned callbacks expose only bool; they do not expose the token created internally. A complete offer-context ledger needs an API extension or application-level integration, not just the logging example.

Local late-reward notifications are not authenticated server-side verification. No SSV endpoint, signed reward validation or durable reward ledger is implemented here.

6. No-ads and persistence#

csharp
MonetizationManager.SetNoAds(true);      // Permanent no-ads.
MonetizationManager.SetTimedNoAds(3600); // At least one hour from now.
bool active = MonetizationManager.IsNoAdsActive;
// MonetizationManager.DisableNoAds(); // Clears BOTH permanent and timed state.

NoAdsSaveData is stored as JSON under PlayerPrefs key bcylyLabs_Monetization_NoAds. It contains a permanent flag and a UTC Unix expiry timestamp. Initialization loads it lazily. It is a local entitlement cache, not receipt verification or tamper-proof storage.

Activating no-ads destroys the banner and resets SafeAreaAdapter layout. Rewarded is intentionally allowed. The timed getter can return false after expiry without raising an event; no automatic banner restoration is implemented. If integrating purchases, keep purchase ownership authoritative and define how restored ownership updates this cache.

7. Consent and privacy extension#

IConsentProvider exposes Name, CurrentStatus, CanRequestAds, RequestConsentAsync and ShowPrivacyOptionsForm. ConsentManager.RegisterProvider adds a provider; GatherAllConsentAsync visits registered providers and returns a combined result. CanRequestAds returns true when none are registered.

Normal native startup currently does not construct/register AdMobUMPProvider or AppleATTProvider, and MonetizationManager ignores the gather result. Register providers before gathering and modify orchestration to enforce eligibility before SDK initialization or load. Do not simply paste a provider registration after InitializeAsync; that is too late for startup requests.

Keep ATT tracking authorization separate from whether nontracking ad requests are allowed. The shipped ATT provider's denied state is modeled as CanRequestAds=false; design a suitable platform/network eligibility model rather than treating all privacy signals as interchangeable.

ShowPrivacyOptionsForm only selects the first registered provider. Choose a form-capable provider deliberately, expose requirement status, marshal native callbacks before Unity UI work and refresh eligibility after changes. Handle update errors without assuming an exception means permission.

For native SDK behavior, consult the Google UMP guide.

8. Provider contract and registration#

csharp
public interface IAdProviderHandler
{
    string ProviderName { get; }
    bool IsInitialized { get; }
    System.Threading.Tasks.Task<bool> InitializeAsync();
    void ShowBanner();
    void HideBanner();
    void DestroyBanner();
    void RequestInterstitial();
    bool IsInterstitialLoaded();
    void ShowInterstitial(System.Action<bool> callback);
    void RequestRewardedVideo();
    bool IsRewardedVideoLoaded();
    void ShowRewardedVideo(System.Action<bool> callback);
    bool IsAppOpenLoaded();
    void ShowAppOpenAd();
}

ProviderContainer supplies ProviderName, HandlerTypeName and CreateHandler(settings). Its default factory resolves a type by name/reflection and invokes a constructor taking the container and settings. MonetizationSettings stores containers through SerializeReference and selects one by its provider name.

Native adapter compilation is conditional on BCYLY_ADMOB_INSTALLED, BCYLY_APPLOVIN_INSTALLED, BCYLY_LEVELPLAY_INSTALLED or BCYLY_UNITYADS_INSTALLED. The editor symbol manager updates defines and assembly references using dependency detection heuristics.

For a new adapter, keep it in a separate assembly, provide a serializable container, wire a deliberate factory/preservation mechanism, marshal callbacks, track request generations and clean up native subscriptions/resources. The current interface lacks Dispose and session-token parameters; extend it consistently if implementing reliable lifecycle ownership.

Reflection-created handler types/constructors need explicit factories or linker preservation for stripping-enabled IL2CPP builds. An Editor success is not sufficient evidence.

9. Main-thread dispatch and layout#

MainThreadDispatcher creates a DontDestroyOnLoad host, queues Action delegates for Update and hosts watchdog/retry coroutines. Post itself only enqueues; it requires a live initialized host to execute. Avoid calling Unity object APIs directly from SDK worker callbacks.

SafeAreaAdapter exposes BannerHeight, CurrentBannerPosition, OnSafeAreaAdjusted, SetBannerLayout, ResetBannerLayout and GetAdjustedSafeArea. Use a consistent screen-pixel convention when consuming its Rect. Current native adapters mix units and do not honor all positions, so validate and correct those paths before using the adjusted Rect as a layout authority.

10. Native lifecycle requirements#

Interstitial completion must have a consistent definition across adapters and execute once. AdMob should not destroy the current fullscreen object immediately after dispatch; reload after close/failure. App-open needs one foreground owner, enabled/no-ads/fullscreen guards, real closed/failed events, expiration handling and replenishment.

Use per-format isLoading/isShowing state, operation identity and cancellation/cleanup. Current startup has no shared initialization task, provider disposal or full domain-reload-disabled reset. Treat runtime network switching as unsupported until those lifecycles are added.

See the Google interstitial lifecycle and app-open lifecycle when implementing the AdMob fixes.

Testing & Troubleshooting

Test beyond the happy path, diagnose common issues and prepare a deliberate network configuration.

1. Verification levels#

EnvironmentWhat it establishes

This manual describes source behavior and known issues; it does not certify native ad delivery. No dedicated discoverable NUnit/UnityTest suite was found in the package. The demo and diagnostics are development tools, not a substitute for regression tests.

2. Simulator walkthrough#

  1. 01
    Select Dummy and verify your bootstrap references the intended settings asset.
  2. 02
    Enable the formats needed for your test and initialize once in Play Mode.
  3. 03
    Show/hide/destroy a banner and verify layout changes.
  4. 04
    Attempt an interstitial before the initial cooldown; it should be suppressed.
  5. 05
    Show one after the delay, close it and verify pacing before the next attempt.
  6. 06
    Complete a rewarded ad and verify exactly the offered reward is delivered once.
  7. 07
    Close a rewarded ad early and verify no earned reward is granted.
  8. 08
    Enable late-reward simulation; inspect the initial false callback followed by the late event.
  9. 09
    Activate permanent/timed no-ads and verify non-rewarded suppression.
  10. 10
    Restart the application session and verify expected no-ads persistence.

The late-reward path currently needs fixes for duplicate notification and session attribution. A functioning mock button demonstrates the event path, not once-only reward correctness.

4. Diagnostics and build preparation#

The Diagnostics tab checks detected SDKs, selected credentials, platform settings, script defines and presence of build helpers. Treat results as hints and inspect the actual build target.

Current limitations include Android-biased ID checks, SDK detection by folder/manifest heuristics and target-API passing messages without a required-version comparison. A postprocessor file existing does not prove its generated output is correct.

Before release:

  1. 01
    Resolve consent, reward attribution, callback and app-open issues that affect the formats you will ship.
  2. 02
    Pin a deliberately tested SDK version and compile each intended adapter.
  3. 03
    Fix the LevelPlay namespace collision before enabling its define.
  4. 04
    Confirm the runtime asset matches the one edited by the Hub/build tools.
  5. 05
    Confirm live app/unit/game IDs for the correct platform; configure test traffic on development devices.
  6. 06
    Check generated Android/iOS configuration and native dependency resolution.
  7. 07
    Run stripping-enabled Android/iOS device tests and repeated foreground/background cycles.
  8. 08
    Verify reward persistence/compensation and no-ads restoration in your own game.
  9. 09
    Verify your build process rejects unintended Dummy/placeholder configuration.

The supplied release validator only warns for Dummy in batch mode. Interactive warnings can be suppressed through EditorPrefs. It does not provide a fail-closed production gate.

7. Known implementation boundaries#

  • Consent classes and UI exist, but normal native startup does not register/enforce them.
  • Rewarded callback attribution and late-event deduplication have reproduced failures.
  • Interstitial completion semantics differ across adapters; AdMob reload happens prematurely.
  • App-open is partial for AdMob and absent for MAX/LevelPlay/Unity Ads.
  • Initialization, provider disposal, static reset and per-format request cancellation are incomplete.
  • No durable reward ledger, authenticated SSV, internal network waterfall or automatic fallback exists.
  • No-ads is local PlayerPrefs state and timed access uses the device wall clock.
  • Several banner options, height units and expiry notifications need corrections.
  • SDK installation/removal and green diagnostic messages are not proof of a release-ready build.

These boundaries should guide testing and implementation planning. They are not additional hidden setup switches that can be enabled in the Hub.

8. Useful support evidence#

Record Unity version, SDK/plugin version, target device/OS, build configuration, active provider, enabled formats, ad unit/placement, result, event order and reproduction steps. For rewarded issues, retain the offer context and session/token details where available.

Include whether the failure occurred with Dummy or real test ads. Share relevant logs without private account credentials. A screenshot of the Hub helps diagnose configuration, but event logs and native build output are necessary for lifecycle issues.
