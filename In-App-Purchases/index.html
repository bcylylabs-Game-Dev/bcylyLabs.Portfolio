Scope and support#

The included README identifies this package as version 1.0.0. The source reviewed for this guide uses Unity 6000.3.6f1 and Unity Purchasing 5.4.3. These are the reviewed environment versions, not a minimum-version guarantee. The older README's Unity 2021.3+ compatibility claim has not been verified by this documentation work.

The implemented providers are Dummy and Unity Purchasing. The Unity adapter selects Google Play or Apple based on compile target. Amazon catalog export is available; Amazon runtime billing is not implemented here. Unity IAP 5 does not support Amazon: see the official migration guide.

Live subscriptions are disabled by default and have documented implementation gaps. Treat their current support as experimental. This manual describes existing behavior; they do not imply the package passed device/store certification or that the identified code gaps have been fixed.

Quick start#

  1. 01
    Open Tools > Bcyly Labs > Bcyly In-Apps Purchases > IAP Hub.
  2. 02

  3. 03
    Add a product with a stable key and appropriate fulfillment mode.
  4. 04
    Add BcylyIAPButton to a Unity UI Button and enter the same key.
  5. 05
    Enter Play Mode and test the simulator purchase.

For a first isolated demonstration, use Create or Open IAP Demo Scene from the same menu. The demo can reference starter keys that differ from your catalog; check its configured product keys.

Setup & workflowChapter 02

User Guide

Configure the Hub, build a catalog, connect your shop and test the complete purchase experience.

1. What the package does#

bcylyLabs IAP connects your product catalog and Unity shop UI to a simulated store or Unity Purchasing. It provides a setup Hub, purchase/restore buttons, localized price binding, transaction processing and local ownership storage.

There are three separate responsibilities:

  • Store catalog: products and actual prices configured in Google Play Console or App Store Connect.
  • Package catalog: developer keys, store IDs, display fallbacks and fulfillment settings.
  • Game rewards: your game's coins, boosters, lives and other effects, connected through a custom fulfillment handler when needed.

A fallback price is display text. Changing it does not change the actual store price. The built-in counter is separate from your game's wallet.

2. Open the setup tools#

Use Tools > Bcyly Labs > Bcyly In-Apps Purchases > IAP Hub. The Hub contains:

TabPurpose
OverviewSelect/create settings, inspect provider installation and configure runtime options
ProductsAdd and edit products, store IDs and reward modes
Simulator SandboxRun Play Mode purchase simulations and clear test profiles
DiagnosticsInspect available package diagnostics

The Hub is also accessible from Project Settings > bcylyLabs IAP. Select IAP Settings selects the resolved asset in the Project window.

Select the correct settings asset

The Hub supports an active settings asset and registers it in Player Settings' Preloaded Assets. This ensures the asset is loaded in a player build. Use the Hub's settings selector rather than assuming that an asset named BcylyIAPSettings is active.

If no settings exist, the editor creator writes Assets/Resources/bcylyLabs/IAP/BcylyIAPSettings.asset with starter no-ads, coins and subscription products.

Keep one intended active catalog. Runtime fallback loading includes project-specific filenames and can choose a different asset when several catalogs exist. Verify the selected profile in the Hub before editing or building.

3. Configure simulation#

Sandbox modeActual behavior
DisabledRequests the native provider, including in the Editor
EditorAndUnsupportedOnlyUses Dummy in Editor and WebGL; native provider elsewhere
AlwaysSimulateUses Dummy on every target, including mobile devices
Implementation note

Despite the enum name, EditorAndUnsupportedOnly does not test every unsupported desktop platform. Its implementation explicitly checks Editor and WebGL.

Keep Auto Initialize On Awake enabled for the standard workflow. With it disabled, your bootstrap must call BcylyIAP.Initialize() once before registering custom handlers or purchasing.

Allow Sandbox Demo Build bypasses the release build guard for intentional simulated demos. It does not enable real billing. A non-development build with AlwaysSimulate normally fails the package's pre-build check.

Change settings before starting Play Mode. Repeated runtime initialization is not a supported profile-switching workflow in this version.

4. Add products#

In Products, use a preset or add a custom product.

FieldMeaning
KeyStable identifier used by game code and UI, for example no_ads
TypeConsumable, NonConsumable or Subscription
Default Store IDStore-facing product identifier used when no override exists
Google/Apple/Amazon overrideOptional store-specific identifier; Amazon has no runtime adapter here
Fallback TitleTitle displayed by package UI
Fallback PriceTest/fallback text shown before live price metadata is available
Description / IconProduct metadata and optional image
FulfillmentBuiltInEntitlement, SimpleCounter or CustomHandler
Counter AmountIncrement for a consumable using SimpleCounter

ID resolution is: provider override -> default store ID -> developer key. The key and store ID may differ. Match store IDs exactly to products configured in the store console. Keep keys and IDs stable after release; renaming a key does not migrate saved ownership.

Choose a fulfillment mode

Use caseRecommended setup
Permanent feature such as no-adsNonConsumable + BuiltInEntitlement; connect ownership to the feature
Simple isolated demo counterConsumable + SimpleCounter
Existing game wallet or reward bundleCustomHandler with durable transaction deduplication
SubscriptionSimulator experiments only until the live implementation gaps are resolved
Implementation note

Do not configure a coin purchase as BuiltInEntitlement and assume coins will appear. A SimpleCounter increment is stored under the product key and can be read through GetCounter; it does not automatically update your game wallet or provide a spending API.

5. Add a purchase button#

  1. 01
    Create or select a Unity UI Button.
  2. 02
    Add bcylyLabs > IAP > bcylyLabs IAP Button.
  3. 03
    Set Product Key to the catalog key.
  4. 04
    Optionally assign price/title labels and an icon image.
  5. 05
    Enable Disable If Purchased or Hide If Purchased for owned permanent products.
  6. 06
    Connect feedback events to sound, animation or purchase messages.

The component registers its own click listener. Do not additionally wire the Button's OnClick to a second purchase call.

onPurchaseSuccess and onPurchaseFailed are feedback hooks. Deliver paid rewards in the fulfillment pipeline, not these UI events. Otherwise another scene, restore or duplicate event may deliver rewards inconsistently.

The component prevents repeated clicks on that button while processing. Multiple buttons or scripted requests for the same product are not globally serialized by this version.

6. Display a price#

Either assign the purchase button's price label or add bcylyLabs IAP Price Text to a separate label and set its Product Key.

The package tries initialized provider metadata first, then the catalog fallback. Unknown keys return a generic $0.99 fallback through the facade, so a displayed price alone does not prove the key exists.

TextMeshPro fields compile when the assembly's TMP_PRESENT package version define is satisfied. Legacy Unity UI Text fields are also available. The settings UI framework choice controls custom inspector presentation; it does not install dependencies or change actual store metadata.

7. Add restore purchases#

Add bcylyLabs IAP Restore Button to a Button.

ModeBehavior
AutoVisible in simulation and Apple targets; hidden on other targets
AlwaysShowForces visibility
AlwaysHideForces hiding

Apple uses the store extension restore request. Other targets scan cached receipt-bearing non-consumables/subscriptions. Dummy restore only reports simulated success; it does not reconstruct purchases after deleting local storage.

Restore is for recoverable ownership, not replaying spent consumable balances. A successful restore callback does not guarantee that all asynchronous custom reward validation/fulfillment has finished. Refresh final ownership using entitlement events.

8. Connect no-ads#

A purchased entitlement does not automatically configure your advertising SDK. Use your game integration or subscribe to BcylyIAPAdsBridge.OnNoAdsStatusChanged in code. The bridge defaults to product key no_ads; set its NoAdsProductKey if yours differs.

The bridge emits state changes and has Unknown, Owned and NotOwned states. It does not directly call an ad manager. For bundles granting no-ads, connect the bundle's reward/ownership explicitly; one default bridge key does not represent every bundle.

9. Test a purchase#

  1. 01
    Set an appropriate simulation mode and enter Play Mode.
  2. 02
    Confirm the service/provider initialized.
  3. 03
    Click the shop button and approve or cancel the simulator sheet.
  4. 04
    Check the expected entitlement, built-in counter or custom game reward.
  5. 05
    For permanent products, verify the button disables/hides as configured.
  6. 06
    Stop/restart Play Mode and verify persisted state.

The Hub also provides Simulate Buy and simulated restore in Play Mode when Dummy is active. Simulations do not prove native store setup or receipt verification.

Use Clear Sandbox Profile Data for isolated test resets. This clears package ownership/journal data, not your game's separate wallet or PlayerPrefs. Clearing the live profile can remove local transaction deduplication history; reserve it for controlled test accounts/devices.

10. Move to real stores#

Configure products and test access in the target store, install/verify Unity Purchasing, select the correct target and replace simulation with native mode. For Google local validation, supply the public key. For custom-server validation, supply a working receipt validation endpoint.

Run the device scenarios in Testing and Troubleshooting. Fix the documented reward and provider gaps before treating this integration as production ready.

Runtime referenceChapter 03

Developer Reference & API Examples

Integrate purchases with your game through the public API, events and durable fulfillment contracts.

Namespace: BcylyLabs.IAP. UI namespace: BcylyLabs.IAP.UI. Ads bridge namespace: BcylyLabs.IAP.Integrations.

Architecture and lifecycle#

text
UI / game code
    -> BcylyIAP static facade
    -> BcylyIAPService
    -> IStoreProvider (Dummy or Unity Purchasing)
    -> BcylyIAPOrder
    -> BcylyTransactionJournal
        -> IValidationPolicy
        -> built-in fulfillment OR IFulfillmentHandler
        -> BcylyIAPStorage commit
        -> success/entitlement events
        -> background store acknowledgment

BcylyIAPService creates a persistent GameObject on demand. Auto-bootstrap runs before scene load when settings enable it. Providers register factory delegates during subsystem registration. Provider initialization triggers startup acknowledgment recovery and a foreground validation/custom retry loop approximately every 15 seconds. Focus regain also requests a validation/custom retry sweep.

Use one initialization per application session. InitializeService currently has no idempotent initialization guard or full provider disposal. Calling Initialize() repeatedly rebuilds the journal and can discard handler registrations.

Adding facade event listeners can create the service object; that alone does not initialize its store or journal. Read-only facade queries generally use the existing service and do not bootstrap it.

Public facade#

MemberPurpose / result
bool IsInitializedActive provider reports initialized
bool IsSimulationActiveService selected simulation

bool IsPurchased(string key)Read local entitlement ownership; intended for permanent products
int GetCounter(string key)Read built-in product counter; zero if unavailable
string GetLocalizedPrice(string key)Provider price or display fallback
SubscriptionInfo GetSubscriptionInfo(string key)Subscription information; may be null without a service
bool HasSubscriptionAccess(string key)True when returned info grants access

Product keys must match the catalog. Although catalog searches ignore case, not every storage/callback dictionary uses the same comparison behavior. Use consistent exact key spelling throughout the game.

Purchase example

Attach this script to a GameObject and connect BuyCoins to a UI action. Choose either this approach or the package's purchase button listener for an individual button.

csharp
using BcylyLabs.IAP;
using UnityEngine;

public sealed class ShopPurchaseExample : MonoBehaviour
{
    public void BuyCoins()
    {
        if (!BcylyIAP.IsInitialized)
        {
            Debug.Log("Store is still initializing.");
            return;
        }

        BcylyIAP.Purchase("coins_500", result =>
        {
            switch (result.Status)
            {
                case PurchaseStatus.Success:
                    Debug.Log("Purchase fulfilled: " + result.ProductKey);
                    break;
                case PurchaseStatus.Cancelled:
                    Debug.Log("Purchase cancelled.");
                    break;
                case PurchaseStatus.Pending:
                    Debug.Log("Purchase pending: " + result.ErrorMessage);
                    break;
                case PurchaseStatus.Failed:
                    Debug.LogWarning(result.ErrorMessage);
                    break;
            }
        });
    }
}
Implementation note

Do not grant coins again inside the completion callback. Success means the pipeline considers fulfillment complete; it does not mean background store acknowledgment has finished.

PurchaseResult exposes Status, ProductKey, TransactionId, ErrorMessage and IsSuccess. Pending is not a terminal payment rejection. The current service removes a request callback after delivering a Pending result; later fulfillment is observed through global events rather than a second invocation of that callback.

Events

EventSignatureMeaning
OnInitializedActionProvider initialization completed
OnInitializeFailedAction<string>Provider initialization reported an error
OnPurchaseSuccessAction<BcylyIAPProduct>A new journal fulfillment emitted success
OnPurchaseFailedAction<BcylyIAPProduct, string>Non-success pipeline outcome; currently includes Pending
OnEntitlementsChangedActionRefresh ownership/access UI

Subscribe in OnEnable and unsubscribe in OnDisable for ordinary scene components. Also read current state when enabling; initialization can precede subscription. Keep observers short and exception-safe. These events are notifications, not a durable reward delivery mechanism.

Some early validation failures returned directly by Purchase invoke only the request callback. Do not assume every failure also generates the global failed event.

Restore example

csharp
BcylyIAP.RestorePurchases((success, message) =>
{
    UnityEngine.Debug.Log($"Restore request: {success}; {message}");
});
Implementation note

Do not interpret this callback as a barrier for asynchronous validation/custom delivery. Listen for entitlement changes and read the resulting ownership.

Catalog model#

BcylyIAPProduct contains key, type, defaultStoreId, per-store overrides, fallback display metadata, icon, fulfillment and counterAmount. Id is an internal GUID and RegenerateInternalId() creates another GUID. Saved ownership currently uses keys, so the GUID does not make key renames safe.

GetEffectiveStoreId(provider) chooses override, then default ID, then key. BcylyIAPSettings supports FindProductByKey, FindProductById and FindProductByStoreId.

Settings resolution uses the cached instance; Editor preloaded assets and active EditorPrefs selection; loaded settings objects; project-specific Resources filenames; the default Resources path; then a Resources-wide fallback. Prefer one deliberate preloaded catalog over relying on fallback order.

Custom fulfillment contract#

Use CustomHandler for rewards stored outside the package's counter/entitlement file. Register after the journal is created. With auto-init enabled this is normally possible in scene startup; with manual initialization call Initialize once first. Missing handlers cause orders to defer until registration.

csharp
public interface IFulfillmentHandler
{
    System.Threading.Tasks.Task<FulfillmentResult> FulfillAsync(
        BcylyIAPOrder order, BcylyIAPProduct product);
}
ResultHandler must mean
SuccessRewards and transaction identity were durably committed
AlreadyAppliedThe same transaction was previously durably applied
RetryableFailureNo completed delivery can be asserted; retry later
TerminalFailurePermanently reject delivery with an understood reason
Implementation note

The journal calls the handler before committing its own fulfillment record. Therefore the handler must provide its own durable idempotency. An in-memory HashSet or a separate PlayerPrefs flag written after granting rewards does not close the crash window.

Required wallet integration pattern

The following is an integration template. DurableWallet.ApplyBundleOnceAsync is an application API you must implement; it is not part of this package.

text
ApplyBundleOnceAsync(transactionIdentity, rewardBundle):
    start durable wallet transaction
    if transactionIdentity already exists:
        return AlreadyApplied
    validate that the entire bundle can be delivered
    update every wallet/inventory value in the bundle
    insert transactionIdentity into the processed-order ledger
    commit wallet values and processed identity together
    return Success

Pass order.CompoundTransactionId as the identity. For a server wallet, enforce a unique transaction identity and authorize the reward from verified store/product information. For local storage, one atomic persisted snapshot must include both balances and processed IDs. Report temporary failures rather than acknowledging a partial grant.

Implementation note

Never register a handler that always returns Success without actually delivering and persisting the reward.

Order identity and processing#

BcylyIAPOrder contains ProductKey, StoreTransactionId, Provider, Environment, Receipt, TimestampUtc, RawProviderPayload and IsNativeStoreVerified.

Compound identity format:

text
{Provider}:{Environment}:{StoreTransactionId}

RawProviderPayload is not serialized. FromCompoundTransactionId reconstructs identity for acknowledgment recovery; it does not restore a full receipt/native payload. A valid stable native transaction identity is essential for deduplication.

Journal processing checks quarantine and duplicates, validates, fulfills, persists FulfilledAckPending, schedules acknowledgment and emits success. On successful/already-finalized acknowledgment it attempts CompletedAcked persistence. Deferred validation/custom queues are memory-only; restart recovery before fulfillment depends on store redelivery.

Validation#

ModeImplementation
NonePassthrough accepts the order
LocalSignature / GoogleRSA signature verification with configured Google public key, plus selected receipt identity checks
LocalSignature / AppleChecks wrapper fields/identity and trusts the adapter's native-verification flag
LocalSignature / other providerFalls back to passthrough
CustomServerPOST receipt data to configured URL

Dummy always uses the dummy-only validation policy. Google supports SHA-256 or SHA-1 verification in this implementation. Local Google validation does not currently compare packageName to Application.identifier. Apple wrapper checks are not independent cryptographic verification of the receipt.

Custom server protocol

The request body is JSON:

json
{
  "productKey": "coins_500",
  "storeTransactionId": "store-transaction-id",
  "provider": "GooglePlay",
  "environment": "Live",
  "receipt": "store receipt payload"
}

A successful HTTP response must contain:

json
{ "valid": true, "reason": "" }

For rejection return a successful HTTP response with valid: false and a reason. The implementation treats HTTP 5xx, network errors and timeouts as temporary; other non-success HTTP statuses are rejection. Consequently 429 is currently not retried as a temporary error. Default timeout is 10 seconds.

The client has no configurable authentication headers or account identifier in this protocol. Add the required account/authentication integration for your backend. The server must actually verify store data and identity; echoing valid=true is not receipt validation. The response does not carry wallet rewards, subscription expiry or authoritative balances.

Persistence#

Default files under Application.persistentDataPath:

  • bcyly_iap_sandbox.dat
  • bcyly_iap_live.dat
  • Associated .bak, .tmp and quarantined .corrupt.* files when applicable.

Schema version is 2. The 48-byte binary header contains magic, version, generation and SHA-256 checksum. Payload data is XOR-obfuscated JSON. The checksum detects corruption; it is not keyed authentication or encryption.

Built-in reward effects and journal records share a file commit with memory rollback on save failure. External wallet effects do not share this transaction. Corruption recovery can quarantine consumables; inspect Storage.HasUnresolvedConsumables and reconcile from an authoritative source. There is no complete support/reconciliation UI in this version.

GetCounter reads a cumulative built-in counter. There is no public spending/decrement API in the facade. Do not substitute it for a complete game currency wallet without extending the design.

Ads bridge#

BcylyIAPAdsBridge exposes Initialize(customNoAdsKey), NoAdsProductKey, CurrentState, IsNoAdsActive, OnNoAdsStatusChanged and OnNoAdsStateChanged.

It automatically initializes after scene load and emits ownership changes; subscribers configure their own ad managers. It tracks one product key and does not itself combine all no-ads bundles. Unknown startup state suppresses false revocation notifications.

Extension boundaries#

IStoreProvider supplies initialization, purchase, acknowledgment, restore, price and subscription queries plus lifecycle/order events. ProviderFactory uses resolver delegates so Core does not directly reference provider assemblies.

The shipped Unity adapter mixes legacy initialization/listener APIs with v5 purchase-service confirmation. Its existence does not establish support for older Unity IAP versions. Consult Testing and Troubleshooting before extending or releasing it.

Testing & Troubleshooting

Test beyond the happy path, diagnose common issues and prepare a deliberate store configuration.

Test environments#

EnvironmentWhat it can establish
Dummy simulatorCatalog/UI flow, callbacks, built-in storage and custom game integration

Implementation note

A simulated success does not verify store configuration. This guide describes the implementation; run the verification steps against your own build and test accounts.

Existing verification menus#

Development test sources are guarded by BCYLY_DEV_TESTS. On a test branch/configuration, add that scripting define for the relevant Editor compilation target if the menus are absent, allow recompilation, then use Tools > Bcyly Labs > Bcyly In-Apps Purchases.

Available runners include Phase 1 Storage, Phase 2 Simulator, Phase 3 UI, Phase 4 Store, Phase 5 Release, all phases, and the 12-case production verification runner. They use custom menu execution and Console output rather than conventional discoverable NUnit/UnityTest cases. Keep this define out of normal distribution builds unless needed for development.

The tests manipulate service/static state and test storage. Run in a controlled development session. A broad success message from a mock runner is not evidence that Google/Apple device flows passed.

Moving to Google Play / Apple#

  1. 01
    Confirm the intended active/preloaded catalog and stable product IDs.
  2. 02
    Configure matching products, actual prices and test accounts in the store console.
  3. 03
    Verify Unity Purchasing is installed and the native adapter compiles for the target.
  4. 04
    Use native mode on the device. EditorAndUnsupportedOnly still uses Dummy in the Editor.
  5. 05
    For LocalSignature Google validation, configure the public key. For CustomServer, deploy and test the expected JSON endpoint.
  6. 06
    Complete durable, idempotent custom rewards before using paid purchases.
  7. 07
    Run real sandbox/test-track purchase, cancellation, deferred, restart and restore scenarios.
  8. 08
    Confirm release settings again after testing. Keep live subscriptions disabled until their access/expiry implementation is corrected.

Store-specific operational instructions change; use Unity's purchasing documentation and the target store's current console documentation for account/submission procedures.

Existing pre-build checks#

The package blocks AlwaysSimulate in a non-development build unless Allow Sandbox Demo Build is enabled. It also checks empty/duplicate developer keys and duplicate nonempty default store IDs.

It does not fully validate store override collisions, provider availability, public keys, server configuration or reward durability. Passing this check is one configuration check, not complete release approval.

Known limitations#

  • Amazon runtime billing is absent; JSON export is only a catalog tool. Unity IAP 5 does not support Amazon.
  • Custom reward crash safety depends on a correctly implemented external handler. An application handler must persist its own transaction deduplication.
  • Native deferred callbacks are declared but not connected by the adapter.
  • Acknowledgment retry exhaustion waits for a future initialization rather than a periodic durable queue sweep.
  • Subscription parsing can fail open, offline fallback does not enforce cached expiry, and built-in fulfillment assumes a one-month period.
  • Reinitialization can replace handlers/journal without full old-provider cleanup.
  • One pending callback per product and one restore callback can be overwritten by concurrent callers.
  • Validation/custom pending queues before fulfillment are not persisted; store redelivery is required after restart.
  • Local storage checksum/obfuscation does not prevent intentional tampering.

Support evidence#

When reporting an issue, include Unity and Purchasing versions, target platform, active settings name, sandbox/validation mode, product key/effective store ID, relevant Console errors and reproduction steps. Include whether it occurred in Dummy or a real store test. Preserve transaction IDs for controlled debugging and avoid sharing public-key configuration screenshots alongside private backend credentials.
